# ElectroTech S&OP Application — Functional Specification

## Purpose

A single-user, locally-run Sales & Operations Planning (S&OP) prototype for a fictional electronics manufacturer (ElectroTech Industries). It demonstrates AI-assisted supply chain planning across demand forecasting, constrained supply planning, capacity management, BOM navigation, supplier risk, and executive reporting.

---

## Application Tabs

### 1. Demand Planning

**Purpose:** Manage the 12-month demand forecast by product and channel.

**Features:**
- **Statistical forecast** — generated from 18 months of demand history using trend + seasonality decomposition. Recalculated at startup.
- **Family / Product / Channel toggle** — switch between aggregated family view (default) and granular product × channel rows.
- **Manual overrides** — click any cell to enter a quantity override. Changes are highlighted in blue. All overrides are stored in `manual_forecast_history` with timestamp and user notes (append-only audit trail).
- **Natural language command box** — type plain-English commands to apply bulk overrides:
  - `"increase all B2C products in November by 10%"`
  - `"set FG003 to 500 units in March"`
  - `"clear all overrides for Q4"`
  - Parsed client-side with regex patterns; matched against product/channel/month vocabulary.
- **Revenue vs Budget chart** — monthly forecast revenue vs annual budget target, showing above/below gap.
- **Forecast accuracy scatter** — product × channel accuracy (MAPE) plotted against revenue contribution. Highlights where poor accuracy matters most.
- **Save Plan** — writes all manual overrides to the DB. These become the demand input for the planning engine.

**Key API endpoints:**
- `GET /api/forecast/statistical` — statistical baseline
- `GET /api/forecast/manual` — current manual overrides
- `POST /api/forecast/manual` — save overrides
- `GET /api/forecast/accuracy` — MAPE by product/channel
- `POST /api/forecast/nl_command` — parse and apply NL command (client-side, no backend call)

### 2. Supply Planning

**Purpose:** Run the constrained supply plan and view results.

**Features:**
- **Unconstrained vs Constrained toggle** — shows the gap between what demand requires and what capacity allows.
- **Run Plan button** — triggers the full 4-pass planning engine (see Planning Engine section below). Results are saved to the DB under a `run_id`.
- **Product-level plan table** — per product per month: demand, constrained supply, backlog, ending inventory, days of supply.
- **Resource utilisation heatmap** — colour-coded by plant and resource: green (<85%), amber (85–100%), red (>100%). Shows where overloads occur.
- **Pull-forward pre-build** — the engine automatically shifts production into earlier months when a resource has spare capacity, within a 6-month window.
- **Supply exceptions list** — products and months where constrained supply cannot meet demand (backlog > 0).
- **MRP planned orders** — component-level replenishment orders generated by the engine.

**Key API endpoints:**
- `POST /api/plan/run` — execute planning engine
- `GET /api/supply/plan` — constrained plan results
- `GET /api/supply/exceptions` — backlog exceptions
- `GET /api/supply/pullforward` — pull-forward details
- `GET /api/material/planned_orders` — MRP output

### 3. BOM Navigator

**Purpose:** Explore the bill of materials and component supply picture.

**Sub-modes (tab buttons at top):**

**Structure mode:**
- Expandable tree showing full multi-level BOM: FG → Sub-Assembly → Component → Raw Material
- Each node shows: item ID, name, make/buy, inventory on hand, lead time, supplier (for bought items), supplier reliability score
- Colour-coded reliability: green (≥95%), amber (85–94%), red (<85%)
- Optional: select a month to see planned quantities alongside the structure

**Shortage Impact mode:**
- Shows which finished goods are affected by component shortages
- Traces shortage back through the BOM levels to identify root cause
- Quantifies the revenue impact of each shortage

**Build Peg mode:**
- Enter a finished good, a quantity, and a target ship date
- Calculates time-phased requirements for every BOM level, working backwards by lead time
- Shows: required quantity, on-hand inventory, gap (shortage in red, surplus in green), "need by" date, "order by" date, urgency RAG badge
- Highlights critical path (items with gaps)

**Key API endpoints:**
- `GET /api/bom/<product_id>` — full BOM tree with inventory and plan data
- `GET /api/bom/shortage_impact` — shortage impact by FG
- `GET /api/material/availability` — component availability picture

### 4. Capacity Solutions

**Purpose:** Analyse capacity overloads and evaluate resolution options.

**Features:**
- **KPI strip:** Total overloaded resources · Revenue at risk (€) · Bank holiday capacity lost (days) · Overload total (minutes)
- **View toggle:** Table view or Card view (per resource)
- **Group by Resource toggle:** Collapse the 18 resources × 12 months = 216 rows into 18 collapsible resource groups
- **Per-resource, per-month detail:**
  - Current capacity (minutes/month, after holiday deductions)
  - Unconstrained load (what demand requires)
  - Overload (load − capacity, shown in red)
  - Revenue at risk from this overload
  - **Four capacity scenarios:**

| Scenario | What it adds | Cost basis |
|----------|-------------|-----------|
| Saturday Shift | 8h × Saturdays in month | Standard rate |
| 3rd Night Shift | 9.6h × 5 days × 4 weeks | +25% night premium |
| Combined (Sat + Night) | Both above | Combined cost |
| Holiday Work | Working on bank holidays | +100% Feiertagszuschlag |

  - Each scenario shows: added capacity (min), cost (€), whether it resolves the overload (✓/✗), new utilisation %
- **Cost summary table:** Total cost per scenario across all overloaded resources, with "Overloads resolved" count

**Key API endpoint:**
- `GET /api/capacity/solutions` — full capacity analysis with all four scenarios

## Planning Engine — Detail

File: `planning_engine.py`

### Algorithm: 4-Pass Multi-Level Constrained MRP

```
Pass 0:  Load master data (BOM, resources, inventory, policies, receipts, holidays)
Pass 1:  FG capacity-constrained plan
Pass 2:  Sub-assembly capacity check → shortfall cascades back to FG
Pass 3:  Component availability check → shortage cascades back to SA → FG
Pass 4:  Convergence loop (repeat passes 2+3 up to 5 iterations until stable)
```

### Planning Buckets
- FG demand / constrained build: **monthly**
- Sub-assembly planning: **weekly** (SA lead times measured in days)
- Component availability: **weekly**

### Capacity Calculation
- Resources are planned individually (not at plant level)
- Capacity = `weekly_capacity × 60 min/h × months_weeks_fraction`
- Bank holidays deducted: `daily_capacity = (weekly_capacity_h × 60) / 5`; one deduction per weekday holiday in that month, per plant calendar
- Pull-forward window: 6 months for FG, 3 months for SA

### Inputs
- Demand: manual-adjusted forecast from `manual_forecast_history` (falls back to statistical if no overrides)
- Capacity: `production_resources.weekly_capacity` × calendar
- Inventory: `inventory` table (on-hand quantities)
- Open orders: `expected_receipts` and `open_orders` tables
- BOM: `bill_of_materials` table (multi-level, with quantities and lead times)

### Outputs (stored in DB under a `run_id`)
- `planning_fg_constrained_results` — constrained build and backlog per product per month
- `planning_item_month_results` — SA and component planned quantities
- `planning_resource_month_results` — utilisation per resource per month
- `planning_resource_product_results` — load split by product per resource
- `planning_material_availability` — component availability and shortage flags

## AI Features

All AI features use the **Anthropic Claude API** (`claude-3-5-sonnet` or latest available).

| Feature | Location | What it does |
|---------|----------|-------------|
| NL forecast commands | Demand Planning | Parses text commands into override actions (client-side regex, no API call) |
| Forecast AI assistant | Demand Planning | Answers questions about the forecast in context |
| Analytics Q&A | Analytics tab | Generates and executes read-only SQL from natural language questions |
| General chat assistant | All tabs (blue chat bubble) | Answers ad-hoc questions about the plan, data, or methodology |

**The NL forecast command box does NOT use the API** — it is parsed entirely client-side with regex patterns. All other AI features require the `ANTHROPIC_API_KEY`.

## Limitations (by design)

- **Single user** — no concurrent access control; two simultaneous users would overwrite each other's plan changes
- **Single site** — planning engine does not model multi-site allocation (products are assigned to a plant at setup time)
- **No authentication** — runs locally with no login required
- **SQLite** — not suitable for >1 concurrent writer or very large datasets (>1M planning rows)
- **CDN dependency** — requires internet at startup to load Chart.js, D3, and Leaflet
- **Horizon fixed** — 12-month horizon defined in `app.py`; changing it requires a code edit and re-running the planning engine
